# Claude Code 活用ガイド (Bubilator88 プロジェクト)

このガイドは、Bubilator88 の開発で Claude Code をより使いこなすための人間向けドキュメントです。
Claude Code に読ませるための資料ではなく、開発者 (あなた) が「次に何をすればいいか」を判断するための手引きです。

すでにこのプロジェクトには、かなり整った自動化・記憶の仕組みが入っています。足りていないのは道具ではなく、
「どう頼めば Claude Code の力を引き出せるか」という使い方の型です。このガイドはその型を 6 つの章に分けて説明します。

---

## 1. この環境にすでにあるもの (見取り図)

まず、今この Bubilator88 リポジトリに何が用意されているかを一覧しておきます。

### スキル (`/コマンド名` で呼び出せるもの)

| コマンド | 内容 |
|---|---|
| `/build` | Xcode プロジェクト全体をビルドしてエラーを報告 |
| `/test` | EmulatorCore のユニットテスト (700件超) を実行して結果を報告 |
| `/boottest` | BootTester で D88 ディスクイメージの起動テストを実行しスクリーンショットを確認 |
| `/regression` | 15 シナリオの回帰テスト (`scripts/regression_compare.py`) を実行し、参照画像とのピクセル比較結果を報告 |
| `/ship` (グローバル) | 変更をコミット・プッシュし、PR を作成してマージまで行う |

これに加えて、Claude Code 本体が持っている組込みスキルもあります。特によく使うのは:

- `/code-review` — 今の diff のバグ・重複・非効率をレビュー (`/code-review ultra` はクラウド上の多エージェント版で課金対象)
- `verify` — 変更が実際に動くか、テストだけでなく実機/BootTester で確認させる
- `/loop`, `/schedule` — 定期実行・自己ペースのループ

`/build` `/test` `/boottest` `/regression` は「いま何をしてほしいか」を Claude が自動的に判断して発動することもあります (skill の frontmatter に書いた description がその材料になっています)。迷ったら明示的に `/regression` のように打ち込んでも構いません。

### サブエージェント

- **hardware-researcher**: PC-8801 のハード仕様を調べさせたいときに名指しする。ローカル資料 → 参照エミュレータ (`~/dev/_Emu/` 配下の BubiC / QUASI88 / X88000M) → Web、の順で出典つきで調査してくれます。
- **regression-checker**: `/regression` の内部で使われている分類ロジックの実体。単体でも呼び出せます。

### 自動で動いているフック

普段は意識しなくても、次の処理が裏で自動的に走っています。

1. **バイナリ資産の書き込みブロック**: `.d88` / `.rom` / `.bin` ファイルへの Edit/Write は自動的に拒否されます (誤って ROM やディスクイメージを壊さないため)。
2. **Swift 編集後の自動ビルド確認**: `.swift` ファイルを Edit/Write すると、裏で `swift build` が走ってエラーがあればすぐ表示されます。「編集したらすぐビルドが通るか分かる」体感はこの仕組みによるものです。
3. **通知**: Claude が入力待ちになると macOS 通知が飛びます。長いタスクを頼んで離席しても気づけます。
4. **コンパクション後のルール再注入**: 会話が要約 (compact) されたあとも、`.claude/post-compact-rules.md` の内容が再度読み込まれ、ルールを忘れません。
5. **コミット前回帰ガード (警告型)**: `Packages/EmulatorCore/Sources/` の変更をコミットしようとしたとき、その後 `/regression` を実行していなければ確認を挟みます (strong block ではなく、あくまで念押し)。

### 自動メモリ

過去の会話で得られた調査結果・ユーザーの好み・プロジェクトの経緯は `~/.claude/projects/.../memory/` に自動的に蓄積されています。
会話中に `# 覚えておいてほしいこと` のように `#` から始めて書くと、その場でメモリに保存されます。次回以降のセッションでも思い出してくれます。

## 2. 計画とレビュー (品質を上げる型)

### Plan mode を使う

`Shift+Tab` でモードを切り替えると、Claude はまず「計画」を提示し、あなたが承認してから実装に入ります。

- **悪い例**: 「サブCPUのタイミングを直して」→ いきなり実装が始まり、方針が気に入らなくても後戻りのコストが大きい
- **良い例**: Plan mode で同じ依頼を出す → 提示された計画を読んで「この層ではなく PIO ハンドシェイクを疑ってほしい」等、方針をその場で修正してから GO する

**使いどころ**: 複数ファイルに跨る変更、方針が複数ありえる変更、影響範囲が読めない変更。逆に「typo を直して」のような一手で終わる依頼には不要です。

### 調査と修正を分ける

「原因の分析だけして。修正はまだしないで」という一文を添えるだけで、Claude は勝手にコードを変更せず、まず状況を説明してくれます。原因の見立てが合っているか確認してから修正に進めるので、手戻りが減ります。

### `/code-review` でコミット前に見てもらう

実装が終わったら `/code-review` でバグ・重複・簡略化ポイントを洗い出させます。`/code-review ultra` はクラウド上で複数エージェントが並行レビューする重い版 (課金対象) で、大きな変更や PR 前の最終チェックに向いています。

### 動作検証をさせる (「できました」を鵜呑みにしない)

Claude が「テストが通りました」と言っても、それは「テストが通った」という事実であって「機能が正しく動く」ことの証明ではありません。このリポジトリは検証手段が豊富なので、必ず使わせてください。

- 「実際に BootTester で動かして確認して」
- 「アプリを起動して実際の画面で確認して」
- 「`/regression` で既存動作が壊れていないか確認して」

### 推奨フロー

```
依頼 → (規模が大きければ Plan mode) → 実装 (TDD) → /test → /regression (EmulatorCore を触った場合) → /code-review → /ship
```

## 3. デバッグ・調査の型 (このエミュ開発特有)

### 起動しないゲームの調査を頼むとき

BootTester の環境変数 (`docs/BOOTTESTER.md` 参照) を添えると調査の精度が上がります。特に有用なのは:

- `BOOTTEST_FRAMES` — 何フレーム実行するか
- `BOOTTEST_SCREENSHOT_PATH` — 最終フレームのスクリーンショットを PPM 出力 (Claude は PPM を直接読めます)
- `BOOTTEST_PORT_TRACE_PATH` / `BOOTTEST_PORT_TRACE_PORTS` — I/O ポートの書き込みトレース
- `BOOTTEST_PC_WATCH` / `BOOTTEST_CPU_TRACE_PATH` — PC 監視・命令トレース

依頼文の例:

> 「LUXSOR の Disk B が起動しない。`docs/KNOWN_PITFALLS.md` の §14 にあるとおり、まず Z80 自体を疑わずに FDC / PIO ハンドシェイク / メモリマップ / CRTC の層から調べてほしい。`BOOTTEST_PORT_TRACE_PORTS=fc,fd,fe,ff` でトレースを取って、正常起動する Disk A との差分を見て」

このように「どの層を優先して見るか」を伝えると、無駄な Z80 精査に時間を使わせずに済みます。

### 画面バグはスクリーンショットを貼る

`Cmd+V` で画像をそのまま貼り付けられます。実機や他エミュレータ (QUASI88 / BubiC 等) のスクリーンショットと並べて貼ると、期待値との差が一目で伝わり精度が跳ね上がります。BootTester が出力する PPM ファイルも Claude はそのまま読めるので、`BOOTTEST_SCREENSHOT_PATH` の結果を都度貼る必要はなく、パスを伝えるだけでも構いません。

### 音のバグの頼み方

「コードは同じはずなのに音が違う」というタイプのバグは、多くの場合 **サンプリング段** (decode rate と mix rate の不一致) が原因です。この一言を添えると調査が早まります。最終的な判定は必ず**耳での AB 比較**にしてください (録音機能があるので、修正前後を録って聴き比べさせられます)。

### ハード仕様の疑問

「hardware-researcher で PC-8801 の○○の仕様を調べて」と名指しすると、ローカル資料 → 参照エミュレータのソース → Web、の順で出典つきに調べてくれます。「多分こうだろう」で実装させるより、先に仕様を確定させたほうが手戻りが少ないです。

### ログ・トレースの渡し方

長いログをそのまま貼るより、`tail -200 ログファイル` のように絞ってから貼るとやりとりが速くなります。`BOOTTEST_CPU_TRACE_PATH` で 2 つの実行のトレースを取って `diff` する手法は、「どの命令から挙動が分岐したか」を特定するのに有効です (`docs/KNOWN_PITFALLS.md` にも実例あり)。

## 4. セッション運用 (日常操作)

- **`/clear`**: タスクが変わったら仕切り直しましょう。長い会話を使い回すと、関係ない過去の文脈が精度を下げることがあります。
- **`/context`**: 今のセッションで何がコンテキストを食っているか確認できます。
- **`/compact`**: 会話を要約して続けます。要約後は `.claude/post-compact-rules.md` のルールが自動的に再注入されます (フック §1 参照)。
- **Esc**: 動作中の Claude を止めて、方針を修正して再指示できます。
- **Esc Esc (または `/rewind`)**: 過去のチェックポイントに巻き戻せます。「会話だけ」「コードだけ」「両方」を選べます。**同じ修正を 2 回言い直してもうまくいかないときは、3 回目を粘らずに `/rewind` か `/clear` で仕切り直し、再現手順やログを足して一発で頼み直す**のが結果的に速いです。
- **`claude --continue` / `--resume`**: 前回のセッションから再開します。`/rename` でセッションに分かりやすい名前を付けておくと、あとで探しやすくなります。
- **`#` メモ**: 会話中に「`# ○○`」で始めて書くと、その場でメモリに保存されます。次回のセッションでも Claude が覚えています。
- 通知 (macOS 通知 + push 通知) はすでに ON になっています。長いビルドやテストを頼んだら、画面に張り付かず離席して大丈夫です。

## 5. 並行・自動化 (応用編)

### worktree で並行セッション

`claude --worktree <名前>` で、同じリポジトリの隔離コピー上に別セッションを立てられます。「片方で原因調査、もう片方で別の機能実装」のように並走させたいときに使います。

**このリポジトリ固有の注意**: EmulatorCore のクラスの stored property を増減したあとは `.build` の incremental build が不整合を起こすことがあるため、worktree を切り替えて戻ってきたときも `rm -rf .build` してからビルドし直す判断を忘れないでください。

### ヘッドレス実行

`claude -p "プロンプト" --output-format json` で、対話なしの一括実行ができます。スクリプトからの自動処理や CI 的な用途に向いています。

### `/loop` と `/schedule`

- `/loop` — 一定間隔、またはモデル自身のペースでタスクを繰り返し実行させたいときに使います (例: 長時間かかる回帰テストを回して結果だけ通知させる)。
- `/schedule` — cron ベースで定期実行するクラウドエージェント (routine) を作れます。

### バックグラウンドタスク

長いビルドやテストは裏で走らせて、その間に別の作業を進められます。完了したら通知されるので、待ち時間をブロックする必要はありません。

### GitHub Actions (@claude) — 今回は見送り、導入する場合の手順

現状は `gh` CLI で十分間に合っているため導入していませんが、将来 PR/Issue 上で `@claude` に直接作業させたくなったら:

1. `/install-github-app` を実行
2. GitHub App 連携と Secrets (`ANTHROPIC_API_KEY`) を設定
3. `.github/workflows/claude.yml` が生成され、PR/Issue のコメントで `@claude` を呼べるようになる

詳細: https://code.claude.com/docs/en/github-actions

## 6. アンチパターン集 (やりがちな NG → 改善)

| NG | 改善 |
|---|---|
| 同じ修正指示を 3 回以上繰り返す | `/clear` して、再現手順・ログ・スクショを添えて一発で頼み直す |
| 「なんか変」「直して」だけで依頼する | 期待する挙動と実際の挙動の差、再現条件を一文でも添える |
| 巨大なタスクを一文で丸ごと依頼する | フェーズに分割して依頼する (このリポジトリの TDD ルールとも一致) |
| 「できました」を鵜呑みにする | 「実際に動かして確認して」まで頼む (§2 参照) |
| 使い捨てスクリプトを毎回書かせる | `scripts/` に保存させる (CLAUDE.md のルール)。次回同じ調査をするときに再利用できる |

## 7. 困ったときの早見表

「何を頼めばいいか分からない」ときに、状況からすぐ引けるようにまとめました。

| 状況 | やること |
|---|---|
| ゲームが起動しない / 画面が真っ黒 | §3 のテンプレで `/boottest` + `BOOTTEST_PORT_TRACE_*`。まず「Z80 を疑わず FDC/PIO/メモリマップ/CRTC から」と伝える |
| 画面の色や表示がおかしい | 実際の画面のスクリーンショットを貼る。可能なら実機/他エミュとの比較画像も添える |
| 音がおかしい (コードは合っているはず) | 「サンプリング段 (decode rate / mix rate) を疑って」と伝え、修正後は録音で AB 比較させる |
| PC-8801 のハード仕様が分からない | 「hardware-researcher で調べて」と名指しする |
| 何をどう直すべきか分からない、方針が複数ありそう | Plan mode (`Shift+Tab`) で依頼し、提示された計画を読んでから GO する |
| 直させたいが、まず原因だけ知りたい | 「原因の分析だけして、修正はまだしないで」と明示する |
| 同じ指摘を 2 回しても直らない | 3 回目を粘らず `/rewind` か `/clear` で仕切り直し、再現手順・ログ・スクショを足して依頼し直す |
| EmulatorCore を触った、コミット前に確認したい | `/regression` を実行してから `/ship`。フックが実行忘れを警告してくれる |
| PR にする前の最終チェック | `/code-review` (大きい変更・重要な PR なら `/code-review ultra`) |
| 長時間かかるビルド/テスト/回帰を待つ間、他の作業をしたい | バックグラウンド実行にして進める。完了したら通知が来る |
| 定期的に同じチェックを回したい | `/loop` (その場のペース) または `/schedule` (cron 相当) |
